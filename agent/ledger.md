- 2026-11-08 (a mechanism the serializer cannot NAME is decoration - and a gate that accepts the wrong shape cannot see it): Two facts combined to ship five wrong artifacts past every structural gate. First, `json-marker` already existed for exactly this ambiguity but was declared in a module that loads AFTER the serializer, so in the real export path a marker was an opaque struct the writer rendered as a slot dump. Only its own gate could decode it. The type must live in the layer every consumer loads after, not in the module that happened to need it first. Second, `gate-json=` contained `((and (null got) (hash-table-p want) (zerop (hash-table-count want))) t)` - NIL accepted as equal to an empty object. That is correct for a COUNT and fatal for a DOCUMENT, because NIL is what the serializer turns into boolean false. The assertion was true, the file was wrong, and nothing pointed at the gap. Deleting that line mattered more than adding any new check: a gate must be UNABLE to pass on the shape that produces a wrong document. Then, immediately after fixing it, the same file-writing helper tested `vectorp` before `stringp` and decomposed every string in every artifact into an array of characters - fifth occurrence of that seam in this project. A recurring bug class needs a mechanism (order the predicates in one shared primitive), not another note. And a general lesson about oracles: the hand-rolled writer knew about markers and the JZON path did not, so ONE conversion function called by both is the only durable arrangement; the next writer then inherits it. Proof: 53/53 artifacts byte-identical, parity gate 4/4, 47 gates exit 0.
- 2026-11-08 (nil conflating "absent" with "empty" is invisible to every structural check, because `false` is valid JSON): Nine artifacts in a fifty-three file export rendered an empty collection as `false` instead of `{}` or `[]`. Root: the counts helpers answer NIL for an empty counter, and the wire conversion passed NIL straight through - where the JSON writer emits boolean false. Companion: `field` applies a js-truthiness filter, which is CORRECT for presence tests and WRONG where an empty array is a real value, so `(field origin "relatedChunks")` on `#()` answered nil. And when a truthiness-based accessor exists, audit every call site where the field can legitimately be empty rather than only where it can be missing. Proof: after connecting the marker and switching two read sites to `gethash`, all 53 artifacts went byte-identical and the parity gate reached 4/4.

- 2026-11-07 (a gate whose comparison has a branch that is always true reports green for inputs it never compared; the fix is to prove the comparator REJECTS): Failure pattern, the assets pipeline gate went from 71/78 to a *worse*-looking 62/78 to 68/78 and then to 24 false passes, and every one of those numbers was believable. The comparator's first branch was `((null (json-null got)) (null (json-null want)))` - but `json-null` is a NORMALISER that returns its argument unchanged for anything that is not JZON's null symbol, so `(null (json-null x))` is T for every x. That branch therefore answered T for any two non-null values, which is to say it answered T without comparing. Two consequences: the non-empty arrays were never actually checked (they "passed" on identity of presence), and the genuinely-empty ones could never match `#()`. Better behavior: a comparator needs the same treatment as a gate - assert it returns NIL for pairs that differ - and a `json-null`-style helper whose name promises "is this null" must not be used as a predicate, because it silently is not one. - 2026-11-07 (`\u{b}` is not a Lisp escape and `format` does not process backslashes; both produce text that LOOKS right and a scanner that cannot parse): Failure pattern, `assets.lisp` would not load at all with "Opening paren has no matching closing paren" inside a regex string. Two independent misreadings of the Lisp reader, both of which I had reasoned about confidently before measuring. (1) `(length "a\u{b}b")` is 6 and `(char "a\u{b}b" 1)` is `u`: SBCL reads `\u{b}` as four literal characters, so every `[ \t\n\u{b}\u{c}\r]` class in the file carried a literal `u`, `{`, `}`, and the require scanner's parens stopped balancing. The whitespace class must be built from `(code-char 11)` / `(code-char 12)`. (2) `format nil` copies `~a` substitutions verbatim and never touches backslashes, so `\\\\W` in source becomes `\\W` in the string - a literal backslash followed by `W`, not the `\W` escape. Regex escapes routed through `format nil` need exactly TWO backslashes in source, not four; the doubled form works only in a plain literal where the reader consumes the first pair. Better behavior: when a regex will go through `format`, build the character classes as values and write the escapes at one level, then prove the scanner MATCHES a positive and a negative case before trusting that it compiles - compilation success only means the parens balance, and `requires)` not matching was the assertion that caught the real defect.

- 2026-11-07 (SBCL number semantics: four host assumptions that each produce a plausible wrong answer, and the mutation gate is what finds them): Failure pattern, porting `Number::toString`/`toFixed` to Lisp and running a generated node oracle (50 toString + 90 toFixed cases crossing as IEEE-754 BIT PATTERNS). Five failures, three distinct root causes, every one of which produced a *plausible* number rather than an error: (1) `(format nil "~,Nf" v)` prints the SHORTEST DECIMAL that round-trips, not the stored binary value - 1.45 prints "1.4500000..." while the double is 1.4499999999999999556 - so rounding from the printed text gave 0.15/1dp = "0.2" where JS says "0.1", and 1.005/2dp = "1.01" where JS says "1.00". Exact digits must come from `(rational v)`, i.e. numerator/denominator integer arithmetic. (2) SBCL's `~E` mantissa is not always `d.dddd`: 1e-320 prints as `10.d-321`, so a fixed `exponent+1` n was off by one and printed "1e-321". Normalise with n = exponent + (digits before the point). (3) `(/= nan nan)` does not answer T on SBCL - it SIGNALS floating-point-invalid-operation, so a NaN reaching a type check crashes; use `sb-ext:float-nan-p`. (4) The shortest-round-trip search must tolerate a candidate that OVERFLOWS on read-back: precision 1 for MAX-DOUBLE is "2.e+308", which `read-from-string` signals overflow on, so the loop crashed on the one value needing the search instead of trying precision 2. Also: `toFixed` keeps the sign of a value rounding to zero (`(-0.05).toFixed(0)` is "-0"), and JSON cannot carry -0 or NaN/Infinity, so the oracle emits bits. Better behavior: for numeric porting, generate the oracle from the live engine and cross values as bit patterns, because a decimal round-trip through two float parsers makes a formatting bug look like a parse bug; and assume every host formatting primitive means something subtly different until an oracle says otherwise. Validation: `tools/cl/run-engine.lisp` 140/140 number cases and 59/59 text cases, with the five failures reproduced first and each root cause named by the failing case's bits.
