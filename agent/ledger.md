- 2026-11-06 (a test double that matches on substrings is order-dependent, and widening one matcher silently steals another's input): Failure pattern: renaming the page-world channel from ten `window.__X__` globals to one `window.__CAPTURE__` root required updating `test/browser-e2e.mjs`, whose mock intercepts `inspectedWindow.eval` by substring: `__RECON__.runtime` -> recon-payload fetch, `__RESOURCE_TRACKER_READY__` -> poll, `__RECON__` -> recon export. The natural rewrite, `recon.runtime`, is ALSO a substring of the recon export expression (`var runtimeItems=recon.runtime||[]`), and matchers are tested in order, so the recon export started returning a runtime-payload stub and the whole export came back empty. The symptom was misleading twice over: the e2e timed out at 61s instead of 2.5s (the poll never saw `ready`, because the poll's own matcher had also been rewritten to a spelling the expression no longer contained), and the first failure message named a missing runtime layer rather than the matcher. Better behavior: a substring matcher must be unique to the expression it selects - pick a fragment that cannot appear in any sibling expression (`var item=list[` is unique to the payload fetch; `recon.runtime` is not) - and when a mock dispatches on expression text, write down for each matcher what makes it exclusive. Corollaries: (1) a test double that runs INSIDE the browser cannot be instrumented with `console.log` to node's stdout, so debugging it means reading the expression strings, not printing from them; (2) restoring a single file from HEAD to bisect a failure is invalid when the system under test is a BUILD - `dist/` was regenerated from the new sources, so HEAD's `page.js` ran against a new `injected.js` and produced a third, unrelated failure; bisect by rebuilding, or restore every input the build consumes; (3) a 25x runtime increase on a test is a signal about which loop exhausted, not noise.

- 2026-11-06 (a backslash in a heredoc is not a backslash; the rule is chr(92), not "be careful"): Failure pattern: writing `r"(?:^|)(query|mutation|subscription)|operationName"` through a `python - <<'PY'` heredoc produced `r"(?:^|)(query|mutation|subscription)|operationName"` - the `` collapsed to a single backslash, which Python then read as the BACKSPACE control character, so the constant silently contained five 0x08 bytes and matched nothing. This is the third time in this repo that a backslash-bearing regex died in a quoting layer (see the 2026-11-05 entry for the same seam on BAD_PATH_CHARS). The earlier lesson was recorded as "build the bytes explicitly with chr(92)"; it was then NOT applied, because it reads as advice rather than as a rule. Better behavior: treat it as mechanical and non-negotiable - a backslash that must survive into a file is ALWAYS `chr(92)` concatenation, never a literal in any quoting layer, and the check after writing is `[c for c in text if ord(c) < 9 or 11 <= ord(c) <= 12 or 14 <= ord(c) <= 31]` must be empty, not "the file looks right in the terminal" (a backspace is invisible). Corollary from the same failure: a Python `old in s` assertion failed on text that printed identically to the probe, because the probe's `` was a backspace and the file's was a backslash - when an exact-match assertion fails on visually identical text, suspect a control character before suspecting whitespace, and prefer index-based slicing by function boundary (`s.index("fn ...")` + brace counting) over matching a block that contains escapes.
